01 · Mapa mental del proyecto

Qué aporta cada pieza

La aplicación se divide para que cada responsabilidad tenga un lugar claro. El navegador muestra pantallas; Supabase autentica usuarios y protege los datos; Vercel sirve la versión pública.

03 · Base y cuentas

Supabase conecta autenticación con perfiles

PostgreSQL guarda la información. Supabase Auth guarda credenciales y crea una identidad UUID. Una función de base de datos crea automáticamente la fila de perfil correspondiente.

Instalar o actualizar la base

  1. En Supabase abre SQL Editor.
  2. Para una base nueva, ejecuta supabase/schema.sql.
  3. Ejecuta supabase/migrations/20261015_customer_accounts_and_reputation.sql para perfiles y reputación.
  4. Ejecuta supabase/migrations/20261016_courier_invitations.sql para almacenar el correo único de cada repartidor.
  5. Comprueba que existen customer_profiles, customer_violations y las columnas requeridas de orders y couriers.
La migración crea perfiles para usuarios existentes y un trigger para nuevos registros. La migración de invitaciones añade correo único a couriers. No insertes credenciales directamente en tablas de negocio.

05 · Permisos y operación

RLS es la puerta de seguridad de los datos

RLS significa Row Level Security (seguridad por fila). Aunque el navegador tenga una clave publicable, cada consulta a la base debe cumplir reglas antes de leer o escribir.

Cliente autenticado
Puede enviar pedidos nuevos y ver los de su propio customer_id; actualiza solo nombre y teléfono.
Administrador
Se comprueba app_metadata.role = admin; gestiona pedidos, invita repartidores y controla sus accesos.
Repartidor
Ve pedidos nuevos de su ciudad y los asignados a su perfil activo.
Visitante anónimo
No puede enviar pedidos: debe registrarse o entrar primero.

Cómo opera el equipo

  1. El cliente envía pedido; la base lo registra como nuevos.
  2. Admin revisa datos, cliente y cobertura; asigna a un repartidor.
  3. Repartidor acepta y actualiza recogida, camino y entrega.
  4. Admin observa la tabla actualizada por Realtime y coordina incidencias.
Nunca intentes “proteger” datos ocultando botones solamente. La autorización final debe estar en RLS o en una función SQL con verificación de rol.

06 · Reputación y moderación

Decisiones humanas, reglas automáticas seguras

La aplicación automatiza el registro y el cálculo, no decide si alguien actuó mal. Una persona administradora revisa primero el caso.

1 · Identificar
Cliente y pedido entregado vinculado.
2 · Revisar
Administrador explica la evidencia comprobada.
3 · Registrar
Función protegida crea un evento único.
4 · Reflejar
Trigger resta 20 puntos, con mínimo 0.

Qué está en el código SQL

  • customer_violations guarda pedido, cliente, evidencia resumida, nota interna, fecha y administrador.
  • La llave única sobre pedido y tipo evita un descuento duplicado por la misma entrega.
  • admin_confirm_customer_nonpayment() verifica el rol y comprueba que el pedido esté entregado y pertenezca al usuario.
  • Un trigger actualiza la reputación dentro de la transacción, así registro y cálculo no se separan.
  • admin_set_customer_order_block() permite pausar nuevas solicitudes 1, 3 o 7 días; la puntuación por sí sola no bloquea.
100 puntos iniciales
- 20 por cada impago confirmado por admin
mínimo: 0
sin bloqueo automático

Ejemplo: 100 → 80 → 60
El admin puede limitar 3 días tras revisar el caso.
Por qué así: evita que un repartidor o un visitante pueda acusar y sancionar directamente; se conserva el motivo y el cliente puede verlo en su perfil y contactar a soporte.

07 · Publicación y validación

De los cambios locales a la web pública

  1. Desarrollo: cambiar componentes y SQL en la rama local; usar datos ficticios al probar.
  2. Base de datos: revisar migración y RLS; aplicar el SQL al proyecto Supabase correcto.
  3. Calidad: npm run lint y npm run build.
  4. Control de versiones: confirmar solo los archivos previstos y publicar el commit en GitHub.
  5. Despliegue: Vercel obtiene el commit, usa las variables de entorno y publica HTTPS.
  6. Prueba real: abrir cuenta cliente, comprobar que el acceso continúa directo a /pedido, revisar historial y estados.
  7. Equipo: probar la invitación y pausar/reactivar un repartidor solo con la clave de servidor configurada.

Checklist de aceptación

  • La cuenta se crea y el correo se confirma si la configuración lo requiere.
  • Una solicitud sin iniciar sesión se rechaza; una cuenta válida sí puede enviar pedido.
  • Nombre y email se asignan desde Auth; teléfono puede quedar vacío.
  • El perfil solo permite consultar pedidos propios.
  • El panel registra un impago solo para pedido entregado con evidencia; el segundo reporte del mismo pedido falla.

08 · Mantenimiento

Cómo seguir aprendiendo y ampliar la app

Para cambiar una pantalla
Busca la página en app/; la interfaz suele estar en su componente de components/.
Para cambiar un dato
Actualiza esquema/migración, tipos TypeScript y los formularios o consultas que lo usan.
Para proteger una acción
Añade política RLS o función SQL, prueba rol permitido y rol rechazado.
Para publicar
Revisa lint/build, revisa diff, sube a GitHub y comprueba el despliegue de Vercel.

Funciones futuras que requieren diseño adicional

  • Subida real de fotos a Storage con permisos privados y políticas de acceso.
  • Pago en línea, reembolsos y conciliación, si se decide abandonar efectivo.
  • GPS en vivo y consentimiento/retención de ubicación.
  • Apelaciones, reglas de recuperación de reputación y proceso de revisión de disputas.
Antes de añadir una función, define quién puede usarla, qué datos exige, quién puede leerlos, qué ocurre cuando falla y cómo se prueba.
